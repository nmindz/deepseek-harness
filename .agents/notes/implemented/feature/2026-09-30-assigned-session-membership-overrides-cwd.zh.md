# Agent Note：显式的会话分配优先于目录匹配

状态：implemented

[English](2026-09-30-assigned-session-membership-overrides-cwd.md) | 中文

## 问题

一个会话只有在其头部 `cwd` 解析到工作区的规范路径时才属于该工作区（`WorkspaceEntity.sessionIds` 按这一事实过滤持久账目，`attachSession` 拒绝任何其他头部）。这条规则带来正确的自动分组，却也是一道天花板：在子文件夹里启动、从未注册的目录里用 CLI 启动、或目录已被移动的会话，会落入“未分组”并永远留在那里。删除工作区会把它的会话散落到“未分组”，除了在同一路径重建注册别无回头路——即便如此也只有 cwd 匹配的会话会回来。用户对分组没有发言权。

## 决策

工作区记录携带 `assignedSessionIds`，即用户显式移入的已记账会话；它始终是 `sessionIds` 的子集。成员规则变为“已记账，且被分配或 cwd 匹配二者居一”：`WorkspaceEntity.sessionIds` 无论头部 cwd 如何都保留被分配的 id，`mutate` 中的持久裁剪保留被分配的 id、并把分配集合收窄为裁剪后账目仍持有的 id，`detachSession` 从两个数组中移除该 id，`validateStoredState` 拒绝重复的、或不在自身账目中的分配 id。自动成员资格不变：会话仍只通过目录匹配自行加入，不带 `assigned` 的 `attachSession` 仍校验 cwd。

- **一个操作完成移动。** `WorkspaceRegistry.moveSession(sessionId, workspaceId?)` 在注册表的串行链上运行：未知目标、已归档目标（`WorkspaceArchivedError`）与未知会话在任何写入之前被拒绝；当前持有者通过记录层面的 `accounts()` 找到，因此被 cwd 过滤掉的候选也会被释放；先写分离，再写目标的 `attachSession(sessionId, { assigned: true })`。被中断的移动因此只可能让会话落到“未分组”，绝不会双重归属，启动时的一主校验保持原样。无目标的移动只做分离。
- **`assigned` 读取头部但不读其 cwd。** 会话仍必须存在（`readSessionHeader` 拒绝未知 id），所以“救援”场景——头部 cwd 缺失或不再解析——正是分配的用武之地。
- **分叉随行。** API 会话控制器把被分配成员的分叉以 assigned 方式挂到同一工作区；cwd 匹配成员的分叉照旧挂接。
- **注册表全局集合不动。** 被移动的会话保留其置顶与归档标记；浏览器本地的手动顺序像对待任何新成员一样，把新来者安置在目标账目的首位。

会话的 `cwd` 从不改变：工具继续在会话原本运行的地方运行，从目标分组发起的新会话仍在工作区自己的路径中启动。侧栏的“移动到…”对话框会说明这一点。

## 考虑过的替代方案

**改写会话头部的 cwd。** 能让目录匹配重新成立，但头部按设计是不可变的，而且会话的工具会跑在用户从未选择的目录里。

**自动把未分组会话归到最近的祖先工作区下。** 剥夺了用户的选择，在注册了多个子文件夹的 monorepo 里会猜错；显式移动可逆且点名目标。

**由头部上的每会话 `workspaceId` 推导成员资格。** 归属是携带顺序的工作区侧事实（[域 KV 存储与工作区实体](../../proposed/architecture/2026-07-24-domain-kv-storage-and-workspace.zh.md)）；会话侧指针会成为同一账目的第二个事实来源。

## 后果

记录多了一个数组，每次写入都必须把它维持为账目的子集；过滤与裁剪现在参考两个事实而非一个。对侧栏而言“工作区 = 目录”不再严格成立：被分配的会话会显示在路径并非其 cwd 的工作区下，对话框对此作出说明，包 README 也把它记录为此前“无法移入”限制的替代。换来的是不再有会话被困在“未分组”，被删除工作区的会话可以重新归组，被移动会话的分叉落在其父会话旁边。
